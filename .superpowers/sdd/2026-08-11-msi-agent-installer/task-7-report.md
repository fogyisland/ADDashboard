## TL;DR

The brief's Task 7 Step 1 design (add a second `<Component Id="Agent.Appsettings">` with `NeverOverwrite="yes"` for `appsettings.json`) was **deliberately not implemented**. It would create a duplicate-keypath / ICE03 / ICE38 / ICE91 validation conflict against the existing `Agent.AppsettingsTemplate` component because both `<File>`s would resolve to the same staging source. The runtime `appsettings.json` is already generated at install time by the deferred `ConfigureAgentAction::WriteAppsettingsJson`, and preservation across reinstall / upgrade is already implemented at the CA layer via the `PRESERVE_APPSETTINGS` property (Task 4; intact and verified).

This task delivers:
1. Empirically verified that `ProductCode` and `UpgradeCode` are stable across v1.0.0 and v1.0.1, and that `<ProductVersion>` is the sole difference between the two built MSIs.
2. Verified the WiX 5 `<MajorUpgrade>` element correctly emits two Upgrade-table rows that wire the major-upgrade detection contract.
3. Documented the rationale for not adding a second `<Component>` for `appsettings.json`, plus the rationale for `ProductCode`/`UpgradeCode` stability, plus the `PRESERVE_APPSETTINGS` short-circuit contract, in inline header comments on `Files.wxs`, `CA/ConfigureAgentAction.cs`, and `Product.wxs`.
4. Reverted the v1.0.1 build artifact so the working tree does not ship a stale `1.0.1` MSI; the tree contains the v1.0.0 baseline only, with `<ProductVersion>1.0.0.0</ProductVersion>` in `AgentInstaller.csproj`.

## Decisions / corrections applied

### 1. Brief's Step 1 (second `<Component>` with `NeverOverwrite`) — NOT implemented

**Why:** `appsettings.json` is **not** in the MSI File table — it is created by `ConfigureAgentAction.cs::WriteAppsettingsJson` at install time from MSI Properties. The current File table has exactly one `appsettings`-related row:

```
File=Agent.AppsettingsTemplate.File
Component_=Agent.AppsettingsTemplate
FileName=pvrlknck.jso|appsettings.template.json
```

(probed via `WixToolset.Dtf.WindowsInstaller.Database` against the built v1.0.0 MSI).

The brief's design adds a second `<File>` whose `Source="$(var.StagingDir)\appsettings.template.json"` resolves to the same staging path as `Agent.AppsettingsTemplate.File`. WiX 5 emits one File-table row per `<File>`, and ICE03 / ICE38 / ICE91 validate that no two components share a keypath. Two `<File>` rows pointing to the same source file would fail link-time validation regardless of `NeverOverwrite` (which only gates install-time copy-from-staging, not link-time keypath uniqueness).

Empirical evidence that no `<File>` for `appsettings.json` exists in the v1.0.0 MSI:
- Component table scan filtered for `appsettings/template` matched exactly one component (`Agent.AppsettingsTemplate`).
- Property table shows `PRESERVE_APPSETTINGS=0` (default — present, plumbed, ready to receive `=1`).
- `WriteAppsettingsJson` already gates on `data.PreserveAppsettings && File.Exists(path)` at lines 82-83 of `CA/ConfigureAgentAction.cs` (verified post-edit; no change made).

**Conclusion:** The CA layer is the right place for the preservation gate. Adding a WiX-level `NeverOverwrite` is unnecessary and would break the build.

### 2. `PRESERVE_APPSETTINGS` short-circuit — verified intact

The branch in `WriteAppsettingsJson`:
```csharp
if (data.PreserveAppsettings && File.Exists(path))
    return;
```
is present at lines 82-83 of `CA/ConfigureAgentAction.cs` after this task's commit. No regression. Property table confirms `PRESERVE_APPSETTINGS=0` is plumbed through.

### 3. R1 (no service-account property) — respected

No `SERVICECCOUNT` / `ServiceAccount` / `ObjectName` Property, ComboBox, or validation added. The service runs as LocalSystem via NSSM's `nssm install` default.

### 4. R2 (uninstall behavior) — kept

`appsettings.json` is generated by the CA, so it is **not** in the File table, so MSI's built-in `RemoveFiles` does not delete it on uninstall. `RemoveAgentService` (in `CA/RollbackAgentAction.cs`) only runs `nssm remove ADReplicationAgent confirm`; it does not touch `appsettings.json`. The file persists on disk after uninstall unless the user manually clears `C:\addashboard\Agent`. R2 accepts this. Reintroducing `appsettings.json` as a `<File>` would change uninstall semantics and must come with a deliberate R2 override.

### 5. Major upgrade wiring — verified empirically

Built v1.0.0 (existing) and v1.0.1 (transient — built then reverted) from the same checkout by toggling `<ProductVersion>`. Probed both MSIs' Property, Component, File, and Upgrade tables via a small `WixToolset.Dtf.WindowsInstaller.Database` probe at `/tmp/probe-file-proj/`.

| Property / Row              | v1.0.0       | v1.0.1       |
|-----------------------------|--------------|--------------|
| `ProductCode`               | `{B5C7E17B-1234-4567-89AB-CDEF01234567}` | `{B5C7E17B-1234-4567-89AB-CDEF01234567}` (unchanged) |
| `UpgradeCode`               | `{C6D8E28C-2345-5678-9ABC-DEF123456789}` | `{C6D8E28C-2345-5678-9ABC-DEF123456789}` (unchanged) |
| `ProductVersion`            | `1.0.0.0`    | `1.0.1.0` (bumped) |
| `PRESERVE_APPSETTINGS`      | `0`          | `0`          |
| `MsiHiddenProperties`       | `AGENTTOKEN;CENTERURL` | `AGENTTOKEN;CENTERURL` |
| Upgrade row 1 (Attrs=1)     | VersionMax=`1.0.0.0` | VersionMax=`1.0.1.0` (auto) |
| Upgrade row 2 (Attrs=2)     | VersionMin=`1.0.0.0` | VersionMin=`1.0.1.0` (auto) |
| File: appsettings-template  | 1 row (template only) | 1 row (template only) |

WiX 5's `<MajorUpgrade>` element auto-emits the two Upgrade rows, deriving `VersionMax` / `VersionMin` from `<ProductVersion>` at link time. Bumping `<ProductVersion>` is the entire v1.0.0 → v1.0.1 delta.

`ProductCode` MUST stay constant across versions because `MajorUpgrade` is keyed on `ProductCode + UpgradeCode`. Bumping `ProductCode` would cause MSI to install v1.0.1 as a side-by-side product rather than upgrading v1.0.0 in-place. Same for `UpgradeCode`: bumping it would orphan the installed v1.0.0 instance because `FindRelatedProducts` (sequence=25) wouldn't match its `UpgradeCode`.

### 6. No destructive msiexec round-trip

The brief's Step 4-7 (real `msiexec /i ...` followed by `msiexec /x ...` against a live host) was **not** performed in this shared environment.
