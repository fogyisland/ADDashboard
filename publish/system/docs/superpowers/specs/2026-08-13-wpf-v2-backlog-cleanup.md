## Background

The redesign SDD (12 tasks + 1 fix round, merged 2026-08-13) delivered the metric-centric editor
but parked 9 items in v2 backlog. Three Critical findings were fixed in the C-1/C-2/C-3 fix round;
the 6 remaining items (1 Important, 4 Minor, several cosmetic) need their own SDD.

The most important item is **D3** — the C-1 fix made overrides write-through to the regenerated

the `.pkgproj` sees Warn revert to the catalog default (80). Smoke driver (38/38 pass) caught this
post-merge.

## Architecture

### Data model (D3)

**New type — `Models/MetricOverride.cs`:**
```csharp
namespace PackageDesigner.Models;

public class MetricOverride
{
    public string? Label { get; set; }   // null = use catalog; non-empty = override
    public string? Unit { get; set; }    // same rule
    public double? Warn { get; set; }    // null = use catalog.DefaultWarn
    public double? Crit { get; set; }    // same rule
}
```

**`Models/PackageManifest.cs` change (the only R1 edit):**
- Add: `public Dictionary<string, MetricOverride>? MetricOverrides { get; set; }`
- Nullable so existing `.pkgproj` files deserialize cleanly.

**Spec-rationale XML doc added to `PackageManifest`:** "Per-metric override values live in
`MetricOverrides` (editor-side only; never serialized to manifest.json). The shipped
`manifest.json` inside the package is regenerated by `MetricGenerator` per save."

### Persistence semantics

- **On save:** `MetricEditorViewModel.SaveTo` reads `SelectedMetrics`, for each item with
  non-null `Override`, writes `MetricOverrides[catalogKey] = new MetricOverride { ... }`.
  Only writes entries with at least one non-null field (keeps the JSON compact; absence =
  "no override").
- **On load:** `MetricEditorViewModel` ctor, after the existing `MetricSchema` re-seed loop,
  looks up each entry in `MetricOverrides` and constructs `Selection.Override` accordingly.
- **`MetricGenerator.GenerateManifestJson` signature unchanged.** Override application rule
  (already in code at `Services/MetricGenerator.cs:60-66`) stays the same — falls back to
  catalog when override field is null.

### Rehydration edge cases

- Override for an unknown metric (custom, not in `MetricCatalog.All`): keyed by string,
  same path as catalog metrics. `isCustom: true` carries through.
- Override for a metric that was REMOVED from `MetricSchema` between save and load: override
  silently ignored (the metric doesn't re-seed). Acceptable — same as today's behavior for
  the schema itself.

### Save button (I-3)

**`MetricEditorViewModel` additions:**
```csharp
public string? LastSavePath { get; private set; }
public ICommand SaveCommand { get; }   // RelayCommand wrapping Save()
public ICommand SaveAsCommand { get; } // existing "Save As…" handler moves here
```

**`SaveCommand.CanExecute`:** `!HasValidationErrors && LastSavePath != null`.
First-save UX: LastSavePath is null → user must click "Save As…" to pick a path. After that,
"Save" stays enabled.

**`SaveCommand.Execute`:** calls `SaveTo(LastSavePath!)`. On success → StatusMessage updates.
On validation failure → returns `!Valid`, file NOT written, status bar shows error.

**`Views/MetricEditorView.xaml`:** replace single Save As button with:
```xml
<Button Content="Save"   Command="{Binding SaveCommand}"   Margin="0,0,8,0"/>
<Button Content="Save As…" Command="{Binding SaveAsCommand}" />
```

**`SaveAsCommand`:** opens `Microsoft.Win32.SaveFileDialog`, default filename =
`Manifest.Name + ".pkgproj"`, calls `SaveTo(fileName)`, on success `LastSavePath = fileName`.

**`MainWindow.xaml.cs` Ctrl+S** unchanged from C-2 fix; still delegates to
`MetricEditorViewModel.SaveTo`. The menu handler explicitly opens a dialog. The new in-editor
Save button is the fast path that reuses the path.
