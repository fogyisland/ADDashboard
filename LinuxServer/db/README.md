# db/migrations

Single-file baseline pattern (R158.51 freeze, R158.X.99.31 rebase 2026-10-19).

## Layout

- `1.0.0-baseline.sql` (top level) — MySQL fallback / historical copy. 1:1 with mysql/1.0.0-baseline.sql. Kept because schema-applier.js:177-181 prefers dialect subdirectory but falls back to top level when the dialect subdir is missing.
- `mssql/1.0.0-baseline.sql` — MSSQL authoritative source. Generated by `scripts/r158.42-dump-schema.mjs` (sys.tables / sys.columns / sys.indexes / sys.foreign_keys / sys.views), then enriched with the R158.X.99.31 seed block (sys_roles / role_permissions / system_config / package_policies). MSSQL-specific: `IF OBJECT_ID + GO` + `SET QUOTED_IDENTIFIER ON`.
- `mysql/1.0.0-baseline.sql` — MySQL fallback copy. Mirrors the top-level file byte-for-byte.
- `1.0.0-baseline.js` — R66 data-migration sidecar (migrateInstalledPackagesToTwoTable). Required by schema-applier.js backfillMigrations. **DO NOT DELETE** even when deleting 1.0.X files — it's the only JS migration helper in the schema-applier scope.

## Forward evolution

After R158.X.99.31, future schema changes go in `db/migrations/{mssql,mysql}/1.0.1-*.sql` (semver). The 1.0.X sequence is RESERVED for old incremental files, so semver 1.0.1 is the next slot. schema-applier.js:326 regex (`^(\d{3})-...`) is bypassed for semver filenames — they run via migrationService.upgrade() dirent scan.

## Two install paths

- **Fresh install** (e.g. dashboard_dryrun DB) — `applyAll('mssql', db)` reads `{mssql,mysql}/1.0.0-baseline.sql`. Single statement, all schema + seed.
- **In-place upgrade** (e.g. dev/staging DBs older than 1.0.0) — same `applyAll` works because the file is guarded with `IF OBJECT_ID` / `IF NOT EXISTS`.

## Seed scope (R158.X.99.31)

What is seeded in the baseline SQL:
- 3 rows in `sys_roles` (admin/operator/viewer)
- 4 rows in `role_permissions` (admin=*, op=execute:sync+read:dash, viewer=read:dash)
- 38 rows in `system_config` (necessary K/V — see seed block header for the full exclusion list)
- 14 rows in `package_policies` (1:1 with BUILTIN_PACKAGES, with cron_expr field)

What is NOT seeded (boot runtime seeder writes it):
- `probe_state` — 3 rows of port_role/status/latency. Runtime writes within 1 min of boot.
- `package_scripts` — script_content + script_sha256 + manifest_json. ~80KB per package × 14 = 1.1MB+ of PowerShell. Lives in `center/data/packages/<name>/<ver>/`; `seedBuiltinPackages()` (center/src/services/builtin-packages.js) copies + writes script row IF NOT EXISTS.
- `cron_schedule` rows — DEFAULT_SCHEDULES JS constant in `center/src/services/cron-scheduler.js`. Operator directive Q4 (2026-10-19) "保持 JS 常量".
- Token / secret / checksum rows in `system_config` — install-time generated by `ensureSignatureAndInstalledAt`.

## Re-dumping the MSSQL baseline

When production DB drifts (new column, new table), re-run:

```bash
cd D:\dashboard\center
R158_42_DUMP_FORCE=1 R158_42_DUMP_DIR=D:\dashboard\db\migrations\mssql \
  node scripts/r158.42-dump-schema.mjs
Move-Item -Force D:\dashboard\db\migrations\mssql\1.0.0-current.sql \
                    D:\dashboard\db\migrations\mssql\1.0.0-baseline.sql
```

Then re-run this ship script to re-append the seed block. The seed block is idempotent (`IF NOT EXISTS` guards).
